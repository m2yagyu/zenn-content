# Zenn記事執筆ワークフロー

このリポジトリ(zenn-content)で新しい記事を書くときの標準手順。
執筆スタイル・テーマの詳細な方針は必ずリポジトリ直下の `CLAUDE.md` を読んで最優先する(テーマは過去に複数回改定されているため、このSKILL.mdの記述より `CLAUDE.md` の内容を信頼すること)。

## 0. 宛先を確認する(2026-08-04追加)
`CLAUDE.md` の「宛先の切り分け」に従い、1つの題材から2つの宛先向けに書き分ける。
調査とコード検証は共通で1回だけ行い、そこから2つの出力を作る。

- **Zenn(手順1〜6)**: Pythonは書けるがAIの中身は知らないエンジニア向け。実装・数式まで踏み込む
- **Instagram(手順7)**: プログラミング未経験の完全初心者向け。直感とアナロジーだけで完結させる

Instagramは「Zenn記事の予告編」ではなく、**それ単体で理解が完結する別宛先の作品**として作る。
Zennの本文を要約してスライドにするのではない。同じ題材を、数式もコードも出さずに伝え直す。

## 1. テーマとヒアリング
- テーマ・対象読者・分量感をユーザーに確認する
- 記事の内容や難易度に大きく影響する技術的な分岐(使うAPI/モデル、有料か無料か、依存ライブラリなど)があれば、本文を書き始める前に必ずユーザーに確認する。書いてから手戻りさせない

## 2. アウトラインの提示
- 見出し構成だけを先に提案し、ユーザーの承認を得てから本文を書き始める
- `CLAUDE.md` のスタイル方針(冒頭2行で得られる結果を明示、動くコードを先に見せて理論・数式は後半、数式の前に日本語での直感的な説明を挟む)を反映した構成にする
- **見出しは疑問形にする(2026-08-08追加。実測根拠は `docs/zenn-analysis-2026-08.md`)**。
  「セル1」「セル2」のような手順ラベルの目次にしない。
  Zennはサイドバーに目次を出すので、目次の時点で「読むと何の疑問が解けるか」を見せる。
  - ✗ `セル3：軽量U-Net` → ○ `なぜ全結合ではダメで、U-Netが要るのか`
  - ✗ `数式で理解する` → ○ `この式は物理のどこから来たのか`
- 図の枚数をアウトライン段階で決める。**図はコードより多くする**。
  同ジャンルの上位記事は図10〜20枚に対しコード0〜10個(我々の既存記事は逆になっている)
- 本文8,000字以上・h3で階層を作る構成を狙う(3,000字未満は読まれない)

## 2.5 タイトルを決める(2026-08-08追加)
タイトルは最後に流通量を決めるので、`CLAUDE.md` の「タイトルの付け方」を必ず読んでから決める。
特に守るのは次の3点。

1. **「：」で副題を足さない**。個人アカウントではWIN率17.3%対55.0%で最も差が大きい要因
2. **20〜30字**に収める(50字超は不利)
3. **口語・好奇心の語彙を1つ入れる**(「結局」「そもそも」「〜って何なの？」)

決めたら実測の物差しにかけて、不利な型に当たっていないか確認する。

```bash
python3 scripts/zenn_analyze.py titles   # 型ごとのWIN率と、同ジャンル上位のタイトル実例
python3 scripts/zenn_analyze.py mine     # 自分の既存記事がどの型に当たっているか
```

## 3. コードの動作検証(必須・省略しない)
- 記事に載せるコードは、公開前に必ずこのセッション内で実際に実行して動作確認する。検証できていないコードは記事に含めない
- **記事のコードブロックには作図処理まで含める(2026-08-08追加)**。
  読者がコピペすると記事と同じ図が手元に出る状態にする。
  図を別スクリプトで作ると、記事の数値と図がずれる(実際に乱数列の違いでずれた)
- 本文に載せた出力が本当にそのコードから出るかは、次で機械的に照合する。
  各コードブロックの先頭で `np.random.default_rng(<seed>)` を明示し、再現可能にしておく
  ```bash
  # images/ で実行すると記事用の図もそのまま更新される
  cd images && ../.venv/bin/python ../scripts/verify_article_code.py ../articles/<slug>.md
  ```
- matplotlibの日本語フォントは、環境にあるものを1つ選ぶ書き方にする。
  `font.family` にリストを渡すと存在しないフォントぶんだけ findfont 警告が大量に出る
  ```python
  from matplotlib import font_manager
  _available = {f.name for f in font_manager.fontManager.ttflist}
  for _font in ["Hiragino Sans", "IPAexGothic", "Noto Sans CJK JP"]:
      if _font in _available:
          plt.rcParams["font.family"] = _font
          break
  ```
- 検証にはこのリポジトリ直下の `.venv`(プロジェクト専用の仮想環境)を使う。使い捨てにせず、次回の記事でも再利用する。システムのPython環境には絶対にインストールしない(この方針は全プロジェクト共通のため `~/.claude/CLAUDE.md` にも記載してある)
  ```bash
  # 初回のみ。既に .venv があればそのまま再利用する
  python3 -m venv .venv
  .venv/bin/python -m pip install -q <必要なパッケージ>

  # 実行は常にこのインタプリタを明示的に指定する
  # (source activate はコマンド間で状態が持続しないため使わない)
  .venv/bin/python <script>
  ```
- `.venv/` は `.gitignore` に入れる。依存は `.venv/bin/python -m pip freeze > requirements.txt` で記録し、再現できる状態にしておく
- `.venv` はシステムのPythonから完全に隔離されており(共有されるのは読み取り専用の標準ライブラリのみ)、gitにも入らないので残しても環境を汚さない。ただしtorchなどを入れると1GB近くになるため、ディスクを空けたいときは `rm -rf .venv` して `requirements.txt` から作り直せばよい
- 検証用の使い捨てスクリプトはスクラッチパッド配下に置くが、実行はこの `.venv` のインタプリタで行う
- Google Colab向けのAIデモを書く場合は、ローカルへの大容量モデルダウンロードより、Hugging Face推論APIのような「ダウンロード不要」な方法を優先する。過去にHugging Face Hub上のモデルダウンロードがColab環境で停止し(xet/CDN起因)、初学者には対処不能な複雑さになった教訓があるため
- 記事中の会話ログ・実行結果は、検証で実際に得られた本物の出力をそのまま使う。都合よく作文しない

## 4. 図解
- 図が必要な場合はmatplotlib(データの可視化)またはmermaid(処理の流れ図)で生成する
- mermaidのフローチャートは `graph TD` の一直線構成にし、双方向の矢印やループを作らない(往復矢印があるとレイアウトが詰まって文字が小さくなり読みにくくなることが実際にあった)
- matplotlibで日本語ラベルを使う場合はフォント(例: Hiragino Sans)を明示指定し、文字化けしないことを確認してから保存する
- 画像はリポジトリ直下の `/images/` に保存し、記事内では絶対パス `/images/xxx.png` で参照する(相対パスは不可。GitHub連携で自動的にZennへアップロードされる)

## 5. 記事ファイルの作成
```bash
npx zenn new:article --slug <slug> --title "<タイトル>" --type tech --emoji "<絵文字>"
```
- frontmatterの `topics` を内容に合わせて整える
- 本文を書き終えるまで `published: false` のままにしておく

## 6. ローカルプレビューと公開判断
- 本文完成後、`npx zenn preview` をバックグラウンドで起動し、`curl` でページが200を返すか(構文エラーがないか)だけ機械的に確認する
- 図やmermaidの実際の見た目・レイアウトは機械的に確認できないため、ユーザー自身に `npx zenn preview` をブラウザで開いて確認してもらい、OKをもらってから次に進む
- 問題なければコミット・プッシュする(この時点では `published: false` のまま)
- ユーザーが明示的に「公開する」と言ってから、frontmatterの `published` を `true` に変更し、再度コミット・プッシュする。ユーザーの明示的な合意なしに公開状態を変えない
- publishしたら、続けて手順7のInstagram素材を必ず作成する(毎回セットで行う。ユーザーから改めて依頼されるのを待たない)

## 7. Instagram投稿の作成(publishのたびに必ず行う)
- **宛先はZennと違う**。読者はプログラミング未経験の完全初心者。
  数式・コード・専門用語を出さず、身近なアナロジーと図だけで、その回の題材を伝え切る。
  Zenn本文の要約ではなく、同じ題材の別バージョンとして作る
- 「わからなくてもZennを読めば書いてある」に逃げない。
  画像だけを見た人がその題材を一つ理解して終われる構成にする

### 何を書き、何を書かないか
- **持ち帰ってもらう理解を3つに絞る**。それ以上は入れない。
  Zenn記事の論点を全部縮めるのではなく、3つ以外は捨てる
- **出さない**: 数式、コード、専門用語(softmax、分配関数、perplexity、ロジット、
  Fokker-Planck、パラメータ数など)、ライブラリ名、GPU/CPUの話
- **出す**: 身近なアナロジー、実際の出力の比較画像、「つまり何が起きているか」の一文
- 物理との対応は初心者向けでも捨てない。**数式を見せずに驚きだけを渡す**。
  「比喩ではなく本当に同じ仕組み」と言い切れることがこのアカウントの強みなので、
  そこは残したうえで、裏付けの式はZenn側に置く

参考例(temperature記事をInstagram向けにした場合):
1. フック「AIに同じことを聞いても毎回ちがう答えが返るのはなぜ？」
2. AIは次の1語を「くじ引き」で選んでいる(候補語と確率の棒グラフ)
3. temperatureはそのくじの偏りを変えるダイヤル(低温/高温の実際の出力を並べる)
4. これは本物の温度と同じ仕組み(冷たい水とお湯の中の分子のたとえ)
5. もっと知りたい人はプロフィールのリンクから

持ち帰る3つは「AIは確率で言葉を選ぶ」「温度というつまみがある」「それは物理の温度と同じ」。
softmax・ボルツマン分布・perplexity・エントロピーは一切出さない。

なお `instagram/` に既にある4本分のcaption.txtは、この方針の前(Zenn記事の予告編として)
作ったものなので、書き方の見本にしない。適用は2026-08-04以降の新規記事から。

- 投稿の実行自体は手動(ユーザーがInstagramアプリから行う)。ここで用意するのは画像素材とキャプション文のみ
- 保存先は `instagram/<記事のslug>/` 配下。ファイル名は `slide1_title.png`, `slide2_*.png`, ..., `slideN_cta.png` と `caption.txt`(この命名はすでに運用中なので踏襲する)。記事本体には使わない販促用素材なので `/images/` には置かない
- 画像は **1080x1080(1:1)** で作る。Instagramでリンクがクリックできない前提なので、画像だけで内容が伝わるように作る
  - 1枚目: タイトル+「これを見ると何がわかるか」のフック文
  - 2〜4枚目: 題材そのものの説明(身近なアナロジー→仕組みの図→実際の結果)。ここで理解が完結すること
  - 最終枚: 「もっと詳しく知りたい人はプロフィールのリンクから」。
    Zennへの誘導は**任意の深掘り先**として置く。ここを読まないと意味が通じない作りにしない
    (Zennはエンジニア向けなので、全員を送り込む導線にはしない)
- デザインは既存スライドに合わせる: 背景 `#1c1c1c` / 本文 `#f2f2f2` / アクセント `#3b82f6` / 補助テキスト `#8a8a8a`、角丸の枠線ボックス、余白を広くとる
- 日本語フォントは `plt.rcParams["font.family"] = "Hiragino Sans"` を明示指定する(指定しないと豆腐になる)。生成後、フォント警告が出ていないか確認する
- 記事中の図やモデル出力を使う場合は、**記事と同じコードを再実行して得た本物の出力**を使う。見栄えのために数値や結果を作り変えない
- 可視化する時刻(ステップ)は、変化が実際に見えるものを選ぶ。拡散モデルは形が終盤で急に現れるため、中間コマに `t=400` のような「ノイズと区別がつかない」値を選ぶと進行が伝わらない
- 生成した画像は必ず1枚ずつ目で確認し、文字のはみ出し・重なり・極端な余白がないか点検してから完成とする
- キャプション文を用意する
  - 冒頭2行で「これを見ると何がわかるか」を明示
  - 完全初心者向けなので、Zenn記事のタイトルや専門用語をそのまま流用しない
  - ハッシュタグ例: `#生成AI #AI初心者 #プログラミング初心者 #機械学習 #物理`(内容に応じて調整)
  - 「もっと詳しく知りたい人はプロフィールのリンクから」程度の、任意の誘導文にとどめる
- `instagram/` はgit管理していない(ローカル素材)。記事本体のコミットに混ぜない
- Instagramプロフィールのリンク欄がZenn記事(または記事一覧)を指しているか、ユーザーに確認を促す
