# Zenn記事執筆ワークフロー

このリポジトリ(zenn-content)で新しい記事を書くときの標準手順。
執筆スタイル・テーマの詳細な方針は必ずリポジトリ直下の `CLAUDE.md` を読んで最優先する(テーマは過去に複数回改定されているため、このSKILL.mdの記述より `CLAUDE.md` の内容を信頼すること)。

## 1. テーマとヒアリング
- テーマ・対象読者・分量感をユーザーに確認する
- 記事の内容や難易度に大きく影響する技術的な分岐(使うAPI/モデル、有料か無料か、依存ライブラリなど)があれば、本文を書き始める前に必ずユーザーに確認する。書いてから手戻りさせない

## 2. アウトラインの提示
- 見出し構成だけを先に提案し、ユーザーの承認を得てから本文を書き始める
- `CLAUDE.md` のスタイル方針(冒頭2行で得られる結果を明示、動くコードを先に見せて理論・数式は後半、数式の前に日本語での直感的な説明を挟む)を反映した構成にする

## 3. コードの動作検証(必須・省略しない)
- 記事に載せるコードは、公開前に必ずこのセッション内で実際に実行して動作確認する。検証できていないコードは記事に含めない
- 検証にはこのリポジトリ直下の `.venv`(プロジェクト専用の仮想環境)を使う。使い捨てにせず、次回の記事でも再利用する。システムのPython環境には絶対にインストールしない(この方針は全プロジェクト共通のため `~/.claude/CLAUDE.md` にも記載してある)
  ```bash
  # 初回のみ。既に .venv があればそのまま再利用する
  python3 -m venv .venv
  .venv/bin/python -m pip install -q <必要なパッケージ>

  # 実行は常にこのインタプリタを明示的に指定する
  # (source activate はコマンド間で状態が持続しないため使わない)
  .venv/bin/python <script>
  ```
- `.venv/` は `.gitignore` に入れる。依存は `.venv/bin/python -m pip freeze > requirements.txt` で記録し、再現できる状態にしておく
- `.venv` はシステムのPythonから完全に隔離されており(共有されるのは読み取り専用の標準ライブラリのみ)、gitにも入らないので残しても環境を汚さない。ただしtorchなどを入れると1GB近くになるため、ディスクを空けたいときは `rm -rf .venv` して `requirements.txt` から作り直せばよい
- 検証用の使い捨てスクリプトはスクラッチパッド配下に置くが、実行はこの `.venv` のインタプリタで行う
- Google Colab向けのAIデモを書く場合は、ローカルへの大容量モデルダウンロードより、Hugging Face推論APIのような「ダウンロード不要」な方法を優先する。過去にHugging Face Hub上のモデルダウンロードがColab環境で停止し(xet/CDN起因)、初学者には対処不能な複雑さになった教訓があるため
- 記事中の会話ログ・実行結果は、検証で実際に得られた本物の出力をそのまま使う。都合よく作文しない

## 4. 図解
- 図が必要な場合はmatplotlib(データの可視化)またはmermaid(処理の流れ図)で生成する
- mermaidのフローチャートは `graph TD` の一直線構成にし、双方向の矢印やループを作らない(往復矢印があるとレイアウトが詰まって文字が小さくなり読みにくくなることが実際にあった)
- matplotlibで日本語ラベルを使う場合はフォント(例: Hiragino Sans)を明示指定し、文字化けしないことを確認してから保存する
- 画像はリポジトリ直下の `/images/` に保存し、記事内では絶対パス `/images/xxx.png` で参照する(相対パスは不可。GitHub連携で自動的にZennへアップロードされる)

## 5. 記事ファイルの作成
```bash
npx zenn new:article --slug <slug> --title "<タイトル>" --type tech --emoji "<絵文字>"
```
- frontmatterの `topics` を内容に合わせて整える
- 本文を書き終えるまで `published: false` のままにしておく

## 6. ローカルプレビューと公開判断
- 本文完成後、`npx zenn preview` をバックグラウンドで起動し、`curl` でページが200を返すか(構文エラーがないか)だけ機械的に確認する
- 図やmermaidの実際の見た目・レイアウトは機械的に確認できないため、ユーザー自身に `npx zenn preview` をブラウザで開いて確認してもらい、OKをもらってから次に進む
- 問題なければコミット・プッシュする(この時点では `published: false` のまま)
- ユーザーが明示的に「公開する」と言ってから、frontmatterの `published` を `true` に変更し、再度コミット・プッシュする。ユーザーの明示的な合意なしに公開状態を変えない
- publishしたら、続けて手順7のInstagram素材を必ず作成する(毎回セットで行う。ユーザーから改めて依頼されるのを待たない)

## 7. Instagram投稿用素材の作成(publishのたびに必ず行う)
- 投稿の実行自体は手動(ユーザーがInstagramアプリから行う)。ここで用意するのは画像素材とキャプション文のみ
- 保存先は `instagram/<記事のslug>/` 配下。ファイル名は `slide1_title.png`, `slide2_*.png`, ..., `slideN_cta.png` と `caption.txt`(この命名はすでに運用中なので踏襲する)。記事本体には使わない販促用素材なので `/images/` には置かない
- 画像は **1080x1080(1:1)** で作る。Instagramでリンクがクリックできない前提なので、画像だけで内容が伝わるように作る
  - 1枚目: タイトル+読むと何ができるかのフック文
  - 2〜4枚目: 記事の要点のハイライト(仕組みの図、実際の実行結果、物理との対応など)
  - 最終枚: 「続きはZennで/プロフィールのリンクから」の誘導
- デザインは既存スライドに合わせる: 背景 `#1c1c1c` / 本文 `#f2f2f2` / アクセント `#3b82f6` / 補助テキスト `#8a8a8a`、角丸の枠線ボックス、余白を広くとる
- 日本語フォントは `plt.rcParams["font.family"] = "Hiragino Sans"` を明示指定する(指定しないと豆腐になる)。生成後、フォント警告が出ていないか確認する
- 記事中の図やモデル出力を使う場合は、**記事と同じコードを再実行して得た本物の出力**を使う。見栄えのために数値や結果を作り変えない
- 可視化する時刻(ステップ)は、変化が実際に見えるものを選ぶ。拡散モデルは形が終盤で急に現れるため、中間コマに `t=400` のような「ノイズと区別がつかない」値を選ぶと進行が伝わらない
- 生成した画像は必ず1枚ずつ目で確認し、文字のはみ出し・重なり・極端な余白がないか点検してから完成とする
- キャプション文を用意する
  - 冒頭2行で「読むと何ができるか」を明示(CLAUDE.mdの記事方針と揃える)
  - ハッシュタグ例: `#生成AI #機械学習 #Python #初心者 #物理 #Zenn`(記事内容に応じて調整)
  - 「続きはプロフィールのリンクから」等、Zenn記事への誘導文を入れる
- `instagram/` はgit管理していない(ローカル素材)。記事本体のコミットに混ぜない
- Instagramプロフィールのリンク欄がZenn記事(または記事一覧)を指しているか、ユーザーに確認を促す

## 8. コミット時の注意
- このリポジトリのローカルgit identity(`m2yagyu <mitsu.yagyu@gmail.com>`)を使う。グローバル設定は変更しない
- APIキーやトークンなど秘密情報は `.env` に書かせて読み込む(チャットに直接貼らせない)。もし誤ってチャットに貼られた場合は、検証後に失効(revoke)して新しいものを発行するようユーザーに伝える
