この記事を読むと、ChatGPTやClaudeのAPIで指定する`temperature`が、統計力学の「温度」と数式レベルで同じものであることを、自分の手で測って確認できるようになります。GPUは不要で、前半はnumpyだけ、後半も152Mパラメータの小さなモデルをCPUで動かすだけです。

LLMが次の単語を確率的に選んでいるという仕組みと、`temperature`がその確率を変えるつまみであることは、[Colabでチャットボットを作る記事](https://zenn.dev/m2yagyu/articles/first-ai-chatbot-colab)で扱いました。softmaxの式もそこで一度出しています。**この記事はその続きです。** あの式が統計力学のどこから来たのかを、測りながら辿ります。前提知識は不要で、必要なことは改めて書きます。

`temperature`を上げると出力が多様になる、というのは使っていれば分かります。この記事で確かめたいのはその先で、**なぜ上げると多様になるのか**、そして**その「温度」とは何の温度なのか**です。結論を先に言うと、比喩ではなく、統計力学のボルツマン分布の温度そのものです。

そして記事の後半では、もう一つの事実に触れます。**最新のClaudeには`temperature`が存在しません。** 送るとエラーになります。温度という制御が、フロンティアモデルでは引退しつつあります。

- 本物の日本語LLMに「日本の首都は」と入力し、次に来るトークンの確率分布を温度ごとに測る

数式は後半にまとめます。前半は全部コードです。

## さっさと動かしてみよう

### セル1：4つの数字で温度を作る

まずLLMを持ち出さずに、`temperature`の正体だけを取り出します。次の4つの数字は、モデルが「日本の首都は」の次に来る候補として出した点数だと思ってください。この点数を**ロジット**と呼びます。

```python
import numpy as np

logits = np.array([2.1, 1.8, 0.3, -0.5])
labels = ["東京", "大阪", "京都", "札幌"]


def boltzmann(logits, T):
    """温度Tでのボルツマン分布（= softmax）"""
    z = np.exp(logits / T)      # exp(-E/T) に対応。logit が -E の役割
    return z / z.sum()          # z.sum() が分配関数 Z


for T in [0.1, 0.5, 1.0, 2.0]:
    p = boltzmann(logits, T)
    print(f"T = {T:4.1f}:  " + "  ".join(f"{l}={v:.3f}" for l, v in zip(labels, p)))
```

```
T =  0.1:  東京=0.953  大阪=0.047  京都=0.000  札幌=0.000
T =  0.5:  東京=0.632  大阪=0.347  京都=0.017  札幌=0.003
T =  1.0:  東京=0.505  大阪=0.374  京都=0.083  札幌=0.038
T =  2.0:  東京=0.394  大阪=0.339  京都=0.160  札幌=0.107
```

これが`temperature`の全てです。**ロジットを $T$ で割ってから指数関数に入れ、合計が1になるように割り算する**、それだけです。

$T$ が小さいと、点数のわずかな差が指数関数で拡大され、1位が独占します（$T=0.1$ で東京が95%）。$T$ が大きいと差が圧縮され、4つが横並びに近づきます（$T=2.0$ で東京39%、札幌11%）。

やっていることを一行で言えば、**点数の差を $T$ で割って、差を効かせるか薄めるかを決めている**ということです。

### セル2：二つの極限を確認する

極端な値を入れると、この操作の性格がはっきりします。

```python
for T in [0.01, 100.0]:
    p = boltzmann(logits, T)
    print(f"T = {T:6.2f}:  " + "  ".join(f"{v:.4f}" for v in p))
print("一様分布なら各 0.2500")
```

```
T =   0.01:  1.0000  0.0000  0.0000  0.0000
T = 100.00:  0.2529  0.2522  0.2484  0.2464
一様分布なら各 0.2500
```

$T \to 0$ では1位の確率が1になり、他は完全に消えます。これは常に最高点のトークンを選ぶ動作で、いわゆる**greedy**です。$T \to \infty$ では4つが0.25に揃います。つまり**点数を無視した完全なランダム**です。

`temperature`という一つのつまみが、greedyから完全ランダムまでを連続的につないでいる、というのがここで見えたことです。

なお$T=0.1$で東京が1.000にならず0.953だったのは、東京と大阪の点数差が2.1と1.8で小さいからです。差が小さい候補を切り離すには、より低い温度が必要になります。これも後で物理の言葉で説明できます。

### セル3：エントロピーを測る

「どれくらいばらけているか」を数字ひとつで表したいときに使うのが**エントロピー**です。定義は後半で書きますが、ここでは「選択肢がどれくらい開いているかの目安」と思ってください。

```python
import math


def entropy(p):
    """S = -Σ p log p"""
    p = p[p > 0]
    return -(p * np.log(p)).sum()


print(f"{'T':>6} | {'エントロピー S':>14} | {'exp(S)':>8}")
print("-" * 36)
for T in [0.1, 0.5, 1.0, 2.0, 10.0]:
    p = boltzmann(logits, T)
    S = entropy(p)
    print(f"{T:6.1f} | {S:14.4f} | {math.exp(S):8.3f}")
print(f"\n上限 ln(4) = {math.log(4):.4f}")
```

```
     T |       エントロピー S |   exp(S)
------------------------------------
   0.1 |         0.1909 |    1.210
   0.5 |         0.7470 |    2.111
   1.0 |         1.0433 |    2.838
   2.0 |         1.2665 |    3.548
  10.0 |         1.3807 |    3.978

上限 ln(4) = 1.3863
```

**`exp(S)` の列に注目してください。** $T=0.1$ で1.21、$T=1.0$ で2.84、$T=10$ で3.98です。候補は全部で4つしかないので、上限は4です。

つまり `exp(S)` は「**実質的に何個の選択肢が生きているか**」を表しています。$T=0.1$ では実質1個（東京しかない）、$T=1.0$ では実質2.8個、$T=10$ では実質4個で全部が対等、という読み方です。

この量は機械学習では**perplexity**と呼ばれ、言語モデルの評価指標として毎日使われています。そして統計力学では、実効的な状態数そのものです。この対応は後半で詳しく書きます。

    print(f"  {p_:.4f}  {tok.decode([i])!r}")

### 3位の「「」は何なのか

上位に混じっている `'「'` は、鉤括弧の開きです（等幅フォントではギリシャ文字のΓに似て見えます）。文字化けではありません。

なぜ答えの単語より上位に近い場所にいるのか。日本語では、こう書くことがよくあるからです。

> 日本の首都は**「**東京」です。

つまり「は」の直後に鉤括弧を開いて、答えを囲む形です。

ここが大事な点です。**モデルは「質問の答え」を予測しているのではなく、「日本語の文章がこの先どう続くか」を予測しています。** だから句読点や括弧のような書式も、当然のように候補に上がります。私たちは「日本の首都は」を質問文として読みますが、モデルにとっては単に途中まで書かれた文であって、その続きとして自然なものを確率順に並べているだけです。

「首都」が2位にいるのも同じ理由で説明できます。「日本の首都は首都圏の中心で…」のような続き方があり得るからです。

ここで押さえておきたいのは**語彙数が99,584あること**です。セル1では候補が4つでしたが、本物のモデルは10万個の候補それぞれにロジットを与えています。上の表はそのうち上位8個を見ているだけです。

`F.softmax(logits, dim=-1)` は、セル1で書いた `boltzmann(logits, 1.0)` とまったく同じ計算です。**PyTorchのsoftmaxは温度1のボルツマン分布**、というのが実装レベルの対応です。

## なぜこれが「温度」なのか

ここまで一度も物理の話をせずに来ました。ここから対応を付けます。

### まず身近な例で

水を考えます。水の分子には、互いに引き合って安定な配置に収まろうとする性質があります。一方で温度が高いほど分子は激しく動くので、その配置は崩れます。同じ水が氷にも水蒸気にもなるのは、**このどちらが優勢かを温度が決めているから**です。低温では安定な配置が勝って分子が規則的に並び（氷）、高温では熱運動が勝って自由に飛び回ります（水蒸気）。

言い換えると、温度が決めているのは「**最も安定な状態に留まるか、それとも他のいろいろな状態も試すか**」の度合いです。

LLMのトークン選択も同じ形をしています。モデルは点数が最も高いトークンを選びたい。しかしサンプリングは、点数の低いトークンにも出番を与えようとします。このどちらをどれだけ優先するかを決めているのが`temperature`です。

セル2の結果を、この言葉で読み直せます。$T=0.01$ で東京が確率1.000になったのは、最も安定な状態に凍りついた（氷になった）ということです。$T=100$ で4つが0.25に揃ったのは、すべての状態が対等に飛び回っている（水蒸気になった）ということです。

### 数式で見る

統計力学では、エネルギー $E_i$ をもつ状態 $i$ が温度 $T$ で現れる確率は、**ボルツマン分布**で与えられます。

$$
p_i = \frac{e^{-E_{i}/(k_B T)}}{Z}, \qquad Z = \sum_j e^{-E_{j}/(k_B T)}
$$

$k_B$ はボルツマン定数で、エネルギーと温度の単位を換算する係数です。$Z$ は**分配関数**（partition function）と呼ばれる規格化定数で、$\sum_i p_i = 1$ を満たすために全状態にわたって和を取ったものです。一方、LLMがトークン $i$ を選ぶ確率はsoftmaxで与えられます。

$$
p_i = \frac{e^{\ell_i / T}}{\sum_j e^{\ell_j / T}}
$$

ここで $\ell_i$ がロジットです。二つの式を見比べると、対応はこうなります。

| 統計力学 | LLM |
|---|---|
| エネルギー $E_i$ | $-\ell_i$（ロジットの符号を反転したもの） |
| 温度 $k_B T$ | `temperature` |
| 分配関数 $Z$ | softmaxの分母 |
| ボルツマン分布 | softmax |

**同じ式です。** 比喩でも近似でもなく、`np.exp(logits / T)` と書いた瞬間にボルツマン因子 $e^{-E_{i}/(k_B T)}$ を計算しています。セル1のコードにコメントで書いた `exp(-E/T) に対応` は、そういう意味でした。

なお機械学習の`temperature`は $k_B T$ をまとめて1つの数として扱っています。物理では $k_B$ がエネルギーの単位（ジュール）と温度の単位（ケルビン）を橋渡ししますが、ロジットには物理的な単位がないので、$k_B$ を1と置いた単位系で書いていることになります。

ロジットが $-E$ に対応する、というのは符号の話だけです。モデルは「点数が高いトークンを選びたい」と考え、物理は「エネルギーが低い状態に落ち着きたい」と考える。向きが逆なので符号が付きます。

### なぜ点数差が小さいと低い温度が必要なのか

セル2で、$T=0.1$ でも東京が1.000にならなかった理由に答えます。

物理では、二つの状態がどちらも占められるかどうかは、エネルギー差 $\Delta E$ と温度の比 $\Delta E / k_B T$ で決まります。この比が1より大きければ低い方に凍りつき、小さければ両方が使われます。

東京と大阪のロジット差は $2.1 - 1.8 = 0.3$ でした。$T=0.1$ なら $\Delta E / T = 3$ で、まだ完全には凍りつきません（実際に大阪が4.7%残っていました）。$T=0.01$ にすれば $\Delta E / T = 30$ となり、完全に凍りつきます。

**効くのは温度の絶対値ではなく、エネルギー差との比です。** これは物理でも同じで、だから「室温」が意味をもつのは、対象のエネルギースケールと比べたときだけです。

### エントロピーとperplexity

エントロピーの定義は次のとおりです。

$$
S = -\sum_i p_i \ln p_i
$$

これは統計力学のギブス・エントロピーそのもの（$k_B$ を1とした単位系）で、情報理論のシャノン・エントロピーとも同じ式です。

そして $e^S$ は、**実効的な状態数**を表します。なぜそう言えるかは、$W$ 個の状態が完全に対等な場合を考えると分かります。このとき各確率は $1/W$ なので、

$$
S = -\sum_{i=1}^{W} \frac{1}{W} \ln \frac{1}{W} = \ln W
$$

となり、$e^S = W$ です。これはボルツマンの関係式 $S = k_B \ln W$ で、彼の墓碑に刻まれている式です。

対等でない場合も、$e^S$ は「実質的に何個分に相当するか」という自然な指標になります。セル3で `exp(S)` が「生きている選択肢の数」に見えたのは、偶然ではなくこの関係の帰結です。

**そして機械学習でいうperplexityは、この $e^S$ です。** 言語モデルの論文で当たり前に出てくる評価指標が、統計力学の実効的な状態数と同じものだった、というのがこの記事でいちばんお伝えしたかった対応です。perplexityが低いモデルが良いとされるのは、次に来る語の候補を実質的に絞り込めているという意味で、物理の言葉なら「低温で秩序だった状態にある」ということになります。

セル5の実測値で確かめると、$T \to \infty$ での上限は $\ln V = \ln 99584 = 11.509$ でした。$T=5.0$ で 11.250 まで来ていて、上限に漸近しています。$T \to 0$ では $S \to 0$、$e^S \to 1$、つまり状態数1個です。**第三法則（絶対零度でエントロピーが0になる）が、そのまま出てきています。**

### なぜ引退したのか

代わりに導入されたのが、**adaptive thinking**と**effort**という制御です。前者はモデルが「どれくらい考えるか」を自分で決める仕組み、後者は`low`から`max`までの5段階で全体の思考の深さと消費トークンを指定するものです。

温度という制御が担っていたのは、突き詰めれば「出力のばらつきをどれくらい許すか」でした。これは1トークンごとの局所的なつまみです。一方でadaptive thinkingやeffortは、「この問題にどれくらいのリソースを割くか」というタスク単位の指示です。**制御の粒度が、トークン単位から思考単位へ上がった**と言えます。

物理の比喩を続けるなら、こうなります。温度は系全体に一様にかける熱浴でした。どの分子にも同じ温度がかかります。それに対して現在の制御は、系のどの部分にどれだけエネルギーを注ぐかを状況に応じて配分する、という形になっています。一様な熱浴を仮定した平衡統計力学から、非平衡の制御へ移った、という見方もできるかもしれません。

### 実務上どうすればよいか

**多様性が欲しかった場合**、プロンプトで指示します。`temperature`を上げる代わりに「表現や構成を毎回変えてください」と書きます。デザインのように選択肢が欲しい場面では、「まず異なる方向性を4つ提案してから、選ばれたものだけを実装してください」という形が有効だとされています。

**決定性が欲しかった場合**、`effort`を`low`にしてプロンプトを絞ります。なお`temperature=0`は以前のモデルでも出力の完全一致を保証していませんでした。同じ入力でも実行ごとに違う結果になり得るという点は、変わっていません。

**古い世代を明示的に使う**という選択もあります。`temperature`が必要なら、`claude-opus-4-6`のように使用可能な世代を指定します。ただし新しい世代の性能は使えません。

なおOpenAIのAPIなど他社のモデルでは`temperature`が引き続き使えます。この記事の前半で確認した内容は、そちらでは今もそのまま当てはまります。

## まとめ

`temperature`が統計力学のボルツマン分布の温度そのものであることを、numpyの4行と152Mパラメータのモデルで確認しました。softmaxはボルツマン分布であり、ロジットは符号を反転したエネルギーであり、softmaxの分母は分配関数です。比喩ではなく同じ式でした。

そして機械学習の評価指標であるperplexityは、$e^S$ という実効的な状態数、つまりボルツマンの $S = k_B \ln W$ の裏返しでした。$T \to 0$ でエントロピーが0に、$T \to \infty$ で $\ln V$ に漸近する様子も、実測で確認できました。

一方で、その温度という制御はフロンティアモデルから姿を消しつつあります。トークン単位のつまみから、思考単位の制御へ移りました。とはいえ、softmaxがボルツマン分布であることは変わりません。モデルの内部では今も、10万個の候補に対して分配関数が計算され続けています。
